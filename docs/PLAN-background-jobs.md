# PLAN — Background Jobs (generators that outlive the app)

## Goal
Let the user keep specific runs generating **after the app closes**, controlled from a **Jobs window**.
Today generators are Electron `utilityProcess` children of the app, so they die on quit. This makes
generation opt-in "background" per run: the app becomes a controller/monitor; background generators
are detached processes that survive quit and are reconnected on reopen.

## User model (confirmed with Karl)
- **Opt-in per run**, via a **Jobs window**.
- The window lists the **runs opened/known this session** — seeds browsed (`seed-N`) and custom
  timelines opened (`*.timeline`) — **plus** any background jobs already running (even from a prior
  session). Each row: name, current day/frontier, a **"generate in background" toggle**, running dot.
- Toggle ON → that run keeps generating in the background (survives app close). Toggle OFF → stop it.

## Invariant that governs everything: ONE writer per run
A run db may have **at most one writer** at a time. A run is generated by EITHER:
- the app's own `utilityProcess` (only for the *actively viewed* run that is NOT backgrounded), OR
- a **detached background generator** (for a backgrounded run).
Never both. The WAL reader (main) can always read either — that's what powers live scrub — but there
is never a second writer. Every state transition below preserves this.

## Architecture

### Detached background generator
- Spawn with Electron's own binary in Node mode so it works in the packaged app and needs no system
  node: `spawn(process.execPath, [RUNGEN, '--out', dbPath, '--resume', '--ticks', 'Infinity',
  '--settings', SETTINGS], { detached: true, stdio: 'ignore', env: { ...process.env,
  ELECTRON_RUN_AS_NODE: '1' } }).unref()`. `detached+unref+stdio:ignore` → reparented to launchd, truly
  survives app quit. RUNGEN = absolute path to `tools/scrub/run-gen.mjs` under ROOT (works dev + packaged).
- Seeds pass `--seed N`; custom timelines resume their stored config (seed irrelevant). `--out` is the
  run's real db path (`timelines/seed-N.db` or `~/Documents/GenePool/<name>.timeline`).

### Job registry (survives app restarts)
- `userData/bg-jobs.json`: `{ [dbPath]: { pid, startedAt, kind:'seed'|'timeline', name, seed? } }`.
- Written on background-ON, removed on background-OFF/exit. On startup + on each Jobs poll, PRUNE dead
  entries via `process.kill(pid, 0)` (throws ESRCH if gone). Guard pid-reuse: also record `startedAt`
  and, best-effort, verify the live process's args contain the dbPath (via `ps`) before trusting it.

### Session-known set
- Main keeps an in-memory `Set` of runs opened this session (added by `selectSeed` / `openTimeline`):
  `{ key, kind, name, dbPath, seed? }`. The Jobs list = (session-known) ∪ (alive bg-jobs from registry).
  Not persisted (session-scoped) — except bg-jobs, which persist via the registry so they reappear.

## Lifecycle transitions (all preserve one-writer)
- **Toggle background ON for run R:**
  1. If R is the *actively viewed* run and the app's utilityProcess is generating it →
     `stopGeneratorAndWait()` (kills that writer), then the app's view of R becomes a **read-only live
     scrub** (open a read-only reader on R).
  2. Spawn the detached generator on R; record in registry.
  (R now has exactly one writer: the detached process. The app reads it read-only.)
- **Toggle background OFF for run R:**
  1. `process.kill(pid)` the detached generator; wait for exit (or best-effort); remove from registry.
  2. `collapseToSingleFile(R)` (drop sidecars now that it's idle).
  3. If R is the actively viewed run, the app may resume owning it (start its utilityProcess) — or stay
     read-only until reselect. (Decide: simplest = leave it paused/read-only until the user acts.)
- **Select/open run R in the app (viewing):**
  - If R has a live background job → do NOT start a utilityProcess; open a **read-only reader** and
    live-scrub (WAL lets the reader see the detached writer's commits). Bar/title unaffected.
  - Else → current behavior (utilityProcess generates R).
- **App quit:** detached background generators keep running (they're detached). The app's own
  utilityProcess (the actively-viewed, non-backgrounded run) stops + collapses as today.
- **App reopen:** load registry, prune dead, show alive jobs in the Jobs window; if the user opens one,
  read-only live-scrub it.

## UI — the Jobs window
- An in-app overlay panel (consistent with `#paramsDlg` / `#kpanel` / the graph), toggled by a bar
  button (e.g. a small "jobs" icon). (Alternative: a separate `BrowserWindow`; heavier, deferred unless
  Karl wants a detachable window.)
- Rows: name (seed-N or timeline base name) · current day (polled ~1–2s via a read-only frontier read)
  · running dot · **[Background] toggle**. A stopped/known run shows the toggle off.
- Live frontier reads are cheap (`openRunReader(path).frontier()`); poll while the panel is open only.

## IPC (main ⇄ renderer)
- `jobs:list` → `[{ key, kind, name, dbPath, day, background:bool, running:bool }]` (session-known ∪ registry, pruned).
- `jobs:setBackground({ dbPath, on })` → performs the ON/OFF transition above; returns updated row.
- `jobs:frontier(dbPath)` (or fold into `jobs:list` poll) → day for the row.
- Renderer adds a "jobs" button + panel; polls `jobs:list` while open.

## Determinism & safety
- `run-gen` is unchanged → detached generation is byte-identical to a utilityProcess run (same code,
  same V8 via ELECTRON_RUN_AS_NODE). Nothing to re-prove in the engine.
- **One-writer invariant** is the safety-critical property; every transition above is written to keep it.
  Add a guard: before starting ANY writer (utilityProcess or detached) on a dbPath, assert no live
  registry entry / no live utilityProcess for it.
- Sidecars: a backgrounded run is actively generating → WAL sidecars exist (expected); they collapse on
  Background-OFF (`collapseToSingleFile`) and on the detached generator's own clean exit (extinction).
  A crash still leaves them (accepted).

## Risks & open questions
- **Two-writer regression** is the cardinal risk (corruption). Mitigate with the pre-spawn guard + tests
  that assert a backgrounded run opens read-only in the app.
- **Detached survival on macOS**: verify `detached+unref+ELECTRON_RUN_AS_NODE` truly outlives app quit
  in the *packaged* app (not just dev). Smoke test required.
- **pid reuse / stale registry** after a crash: prune via `kill(pid,0)` + args check; a false-positive
  (dead pid reused) could show a phantom job — low risk, mitigated by the args check.
- **RUNGEN path in the packaged app**: ROOT-relative resolution must hold in `.app` (assets are staged
  at Resources/app). Verify.
- **Disk/CPU**: many background jobs = growth; the Jobs window is the control surface (no auto-throttle —
  flat-out rule stands). Consider showing total disk in the window (nice-to-have).
- **Extinct/finished background run**: the detached generator exits on extinction; the registry prune +
  a clean exit should drop it from the list and collapse its file. Confirm run-gen exits cleanly there.
- **Open question:** when Background-OFF on the actively-viewed run, does the app resume generating it
  (utilityProcess) or stay read-only until reselect? (Lean: stay read-only; simpler, predictable.)
- **Open question:** in-app panel vs a separate OS window for "Jobs window". (Lean: in-app panel.)

## Test plan
- Unit: registry read/write/prune (dead pid dropped; args-mismatch dropped).
- Integration (headless where possible): the one-writer guard rejects a second writer; a backgrounded
  run is read-only-scrubbable while a separate writer advances it (WAL cross-process).
- Manual smoke (packaged app): toggle a run to background, quit the app, confirm the generator keeps
  advancing (frontier grows with app closed); reopen, confirm it shows in Jobs with the right day;
  toggle off, confirm it stops + collapses to a single file.

## Rollout
1. Registry + detached spawn/stop/list + one-writer guard (main), with unit tests.
2. `selectSeed`/`openTimeline` route to read-only when a bg job owns the run.
3. Jobs panel UI + polling.
4. Packaged-app smoke test (survival across quit) + one-writer integration test.

## Hardening from Review 1 (incorporated — supersedes conflicting text above)

### One-writer guard must cover EVERY writer path, not just open/select [P0]
A run owned by a live background job is **read-only in the app**, enforced at *all* mutating handlers:
- `scrub:commit`, `scrub:commitImport`, `timeline:saveAs` — these open their own writable connection
  (`commitParamEdit`/`commitImport` via `DatabaseSync`; `saveAs` via `copyDb`), and today's
  `stopGeneratorAndWait()` only stops the app's `scrub.child`, NOT a detached process. So: if a live
  registry entry owns the target db, these handlers must **refuse** (return a "stop the background job
  first" error the UI surfaces) — or offer to Background-OFF first. `saveAs` on a bg-owned db is also a
  torn-copy risk, so it's refused too.
- `before-quit`: currently would `checkpointClose(scrub.dbPath)` even for a bg-owned (read-only) viewed
  run. It must **skip any dbPath with a live registry entry** (the detached writer owns it).
- Central rule: **before starting ANY writer** (utilityProcess fork, detached spawn, or a commit's
  DatabaseSync) on a dbPath, assert no live registry entry AND no live utilityProcess for it.

### Stop-then-spawn race + silent-lock failure [P0]
- `stopGeneratorAndWait()` resolves on a 3s timeout even if the child never exited, and its "force kill"
  is still SIGTERM. Background-ON must spawn the detached generator **only after a CONFIRMED child
  `exit`** (not the timeout), and the timeout escalation must use **SIGKILL**.
- Add a **writer-side `busy_timeout`** in `sqlite-sink.mjs` (createSqliteSink) — currently the writer
  sets `journal_mode=WAL; synchronous=NORMAL` and NO busy_timeout, so a momentary two-writer overlap
  makes the second writer throw "database is locked" and the detached process dies on startup (feature
  silently fails). A busy_timeout degrades a brief overlap to a short wait. (WAL still means the writer
  never blocks on *readers* — this only guards writer-vs-writer during a handoff.)

### Extinction / Background-OFF cleanup — the APP owns the collapse [P0]
- `run-gen` on extinction does `writer.close()` which leaves the db in WAL with `-wal/-shm` (it does NOT
  collapse; we're not modifying run-gen). So the app reconciles:
  - **Registry prune:** when a registry pid is found dead (`kill(pid,0)`→ESRCH), call
    `checkpointClose(dbPath)` (the real function name — there is no `collapseToSingleFile`) then drop
    the entry. This is the ONLY reconciliation for a detached/`unref`'d process across a reopen (no
    `exit` event survives).
  - **Background-OFF, same session:** we hold the `spawn()` handle → `child.once('exit')` fires (unref
    only drops the ref-count) → then `checkpointClose`.
  - **Background-OFF, cross session:** we hold only the pid → `process.kill(pid)`, then **poll
    `kill(pid,0)` until ESRCH**, THEN `checkpointClose` (else it hits the still-held lock and bails).

### Single-instance lock + atomic registry writes [P0]
- Add `app.requestSingleInstanceLock()` (quit the 2nd instance) — otherwise two app instances fork two
  utilityProcess writers on one seed db AND race `bg-jobs.json`. Background makes reopen-while-running
  normal, so this is now load-bearing.
- Registry writes are **atomic** (`writeFileSync(tmp)` + `rename`); reads tolerate a missing/partial file.

### Smaller fixes [P1]
- **`isMain` guard** (`run-gen.mjs`): `import.meta.url === \`file://${process.argv[1]}\`` fails when the
  path has a space/non-ASCII (packaged `.app` under "My Apps" etc.) → the detached process does nothing
  and exits. Fix to `fileURLToPath(import.meta.url) === process.argv[1]` (or compare via `pathToFileURL`).
  This is now load-bearing (it wasn't when only used for manual CLI).
- **Registry liveness cost:** `kill(pid,0)` per poll (cheap syscall); run the `ps`-args pid-reuse check
  only on first sighting / startup, not every poll.
- **Frontier polling must not leak connections:** open→`frontier()`→`close()` per poll, or cache one
  reader per known run (reuse `scrub.reader` for the active one). Use `frontier()` ONLY (never
  `getPopSeries`, which holds a read cursor across awaits).
- **Fresh-seed parity:** the detached `--settings` must be exactly `JSON.stringify(POOL_SETTINGS)`. In
  practice Background-ON always targets an EXISTING db and `--resume` ignores `--settings`; the guard
  must ensure the detached path is only ever used on a run that already has a keyframe (never a fresh seed).
- **Startup read race:** just after a detached spawn there's no `ready` handshake — the monitor must
  tolerate `frontier()===-1` / a not-yet-created `-wal` and retry rather than error.

### Recommended hardening to evaluate in the 5-panel [P2]
- **Make the OS the one-writer authority, not pid bookkeeping.** Given frequent hard crashes leave stale
  registry entries/orphan pids, consider either (a) a per-db advisory lock auto-released on process
  death, or (b) the detached writer stamping `pid` + a monotonically-advancing frontier "heartbeat" into
  `run_meta`, with liveness = "frontier advanced in the last N s". Then the guard is "is it locked /
  heartbeating?" and `bg-jobs.json` is purely the UI list. This removes the `ps`/pid-reuse bug class and
  is crash-safe. The panel should decide: keep pid-registry + `kill(pid,0)` (simpler, some edge risk) vs
  adopt a lock/heartbeat authority (more robust, a bit more code). No native deps either way.

## v2 — 5-panel synthesis (FINAL buildable spec; supersedes conflicting text above)
All five lenses returned SOUND-WITH-CHANGES. The design shape (opt-in per run, detached generators, app-as-monitor, read-only-when-backgrounded) stands. The authority mechanism CHANGES, and several correctness/UX items are now required.

### A. One-writer authority = `<db>-wal` freshness (writer-AGNOSTIC), NOT the pid registry [P0, decisive]
The pid registry cannot see writers the app didn't spawn — and there are **5 external CLI generators writing these exact `.timeline` files right now**. Opening one in the app would fork a second writer → corruption. So:
- **The guard is a single preflight, called before opening ANY writable connection on a db:** if `<db>-wal` exists and its mtime is within N seconds (a live SQLite writer touches `-wal` continuously), the db is **owned → refuse writable / route read-only**. This detects external writers, is crash-safe (no stale pid phantoms), and needs zero run-gen changes. (Secondary confirmation available for free: `run_meta.frontier` already advances every keyframe.)
- The registry (`bg-jobs.json`) is now **only** the UI list + the pid to `kill()` on Background-OFF. It is NOT the safety authority.
- **Every writer path routes through this one guard:** `startRun`/utilityProcess fork, the detached spawn, `scrub:commit`, `scrub:commitImport`, `timeline:saveAs`, AND `pool:recordStart` (was omitted — it opens its own sink writer and even has a schema-incompatible `snapshots` table). The guard + writer-open must be **atomic** (an async **mutex** serializing all db-mutating ops; re-check freshness in the same synchronous span as the open — no `await` between check and act).

### B. Detached child must hold a power assertion [P0]
There is NO `caffeinate`/`powerSaveBlocker` anywhere today. A detached generator gets **suspended on idle-sleep** → frontier freezes → the feature silently dies when the Mac sleeps after the app closes. Fix: the detached child holds the assertion itself — co-spawn `caffeinate -s -w <childpid>` (assertion tied to the child's lifetime). `powerSaveBlocker` in main is useless (main exits). Document: on battery with the lid closed, sleep still wins; surface "jobs pause while the Mac sleeps."

### C. Foreground↔background handoff must stay seamless [P0, UX]
Playback is local re-simulation, so the main view is already read-only w.r.t. the DB — backgrounding is nearly invisible EXCEPT:
- **Progress signal:** a detached process sends no `scrub:frontier` IPC. When the actively-viewed run is backgrounded, main must **poll `frontier()` and emit `scrub:frontier`** so the main view keeps advancing (else "watch it grow overnight" silently stops at the handoff frontier).
- **Proactive lock + right message:** push a `curBackground` flag to the renderer so ⚙ / Import / Save As **lock proactively** (dim + tooltip / disabled menu items), and show a **dedicated modal** — "This run is generating in the background" with a one-click **"Stop background job"** button — NOT the wrong pure-seed warning and NOT a transient `#err` string.
- **Background-OFF of the viewed run → resume its foreground utilityProcess** (back to normal live+editable), not a frozen read-only limbo.

### D. Detached lifecycle robustness [P0/P1]
- Spawn `child_process.spawn(process.execPath, [RUNGEN, '--seed', String(seed??0), '--out', dbPath, '--resume', '--ticks', 'Infinity', '--settings', JSON.stringify(POOL_SETTINGS)], {detached:true, stdio:<logfile during bring-up, ignore later>, env:{...process.env, ELECTRON_RUN_AS_NODE:'1'}}).unref()`. Note: **`--seed` is mandatory even for timelines** (run-gen hard-exits without it). `--asar=false` stays (spawn can't run a script inside asar).
- **`isMain` fix in run-gen.mjs**: compare realpaths — `realpathSync(fileURLToPath(import.meta.url)) === realpathSync(process.argv[1])` (handles spaces/non-ASCII AND symlinks; today's `file://`+argv compare silently no-ops the detached process on such paths).
- **Attach `exit` listener at spawn** (same session) → on extinction/exit: `checkpointClose` + registry drop + UI update. `unref()` still lets `exit` fire while the app runs.
- **Cross-session stop:** gate the `kill(pid)` behind an identity check (`-wal` fresh / args match via `ps -p <pid> -ww -o command=`) **before** signaling (pid-reuse could SIGTERM a bystander); then poll `kill(pid,0)`→ESRCH with a **SIGKILL escalation** + bounded loop; then `checkpointClose` with a **bounded retry** (it silently bails on a held lock).
- **Writer-side `busy_timeout`** in `createSqliteSink` (defense-in-depth for handoff overlap only — never the primary safety). Add a byte-identical before/after test since it touches all sink callers.
- **`app.requestSingleInstanceLock()`** + atomic registry writes (single in-memory object mutated synchronously, persisted via tmp+rename; never read-modify-write across an await).

### E. Jobs window UX for the overnight-many-runs user [P1]
- **Primary content = running/terminal jobs**; session-known-but-idle runs are secondary (a "+ background a run…" picker), so 20 browsed seeds don't clutter the window.
- **Terminal rows persist** as distinct states until dismissed: "extinct — day N" vs "stopped by you — day N" (the payoff of overnight runs is seeing the outcome — don't vanish it).
- **Interacting with any row adds it to session-known** (so toggling OFF a prior-session job doesn't evaporate its row).
- **Failed start** → toggle snaps back OFF + inline row error. **Missing file** (db deleted/moved — realistic on the flaky mount) → "file missing" row state with a remove action, not a crash.
- Bar **"jobs" button + running-count badge** (+ a `J` keyboard toggle, matching K/G). Row day labeled **"generated to day N"** (the generator frontier, not the playhead). Poll ~1.5s while open (matches the graph).
- **Disk is first-class**, not nice-to-have: show free-disk + per-job growth + a soft warning near a threshold (warn, never throttle — flat-out rule).

### F. Tests (the load-bearing ones the v1 plan missed)
1. **External-writer detection** (most important): start `run-gen --out X --resume` out-of-band, assert the app opens X **read-only** and every writer path (`select`/`open`/`commit`/`saveAs`/`recordStart`) refuses.
2. `recordStart` onto a live/bg-owned db → refused.
3. Cross-session Background-OFF → sidecars actually collapse (no silent bail; retry works).
4. Disk-full / detached write-crash → registry reconciled, dead job pruned, sidecars handled.
5. Single-instance lock → 2nd instance quits without forking a writer / running a collapse.
6. Resume-handoff determinism → a run advanced by the detached generator then adopted by the app is byte-identical at the handoff tick.
7. Packaged-app survival smoke test → quit app, frontier keeps advancing (and the idle-sleep behavior is as documented).

### G. Simplification the panel endorsed
The `-wal`-freshness preflight collapses the pre-spawn guard + the `ps`/pid-reuse machinery + external-writer handling + reopen-while-running into ONE check. Keep `bg-jobs.json` minimal (UI list + kill pid). This is materially less code AND safer than the v1 pid-authority design.
